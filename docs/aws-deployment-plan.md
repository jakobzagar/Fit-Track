# FitTrack AWS architecture

This document is the single AWS record for FitTrack. It describes the planned architecture and decisions and records implementation state and verification as resources are created.

Planned resources, configured resources, and independently verified settings are clearly distinguished.

## Goals and constraints

- The initial scope is one production environment; staging is deferred.
- No custom domain is configured; the initial public entry point will use the default CloudFront hostname. Route 53 is excluded.
- Resources remain private unless public access is required for the ALB or CloudFront.
- Continuously billed resources should not remain idle during learning or long pauses. The app is unavailable when its runtime is stopped or deleted.
- CloudFormation templates are stored under `infra/`; stacks are deployed and inspected through CloudFormation. Actual outcomes and verification are recorded in this document.

## Verification scope

All nine templates are prepared and have passed local formatting and CloudFormation schema checks. They are not deployed, and AWS runtime behavior is not verified. Local application and container test results are evidence for those artifacts only.

Run `npm run infra:check` before creating or updating a stack. Prerequisites and check limitations belong in [infrastructure validation](testing.md#infrastructure-validation); stack creation order and export contracts belong in [the infrastructure guide](infrastructure.md). Record deployed resource IDs and actual verification results here as implementation proceeds.

## Target request and data flow

```mermaid
flowchart LR
    Browser[Browser] -->|HTTPS| CF[CloudFront]
    CF -->|Default behavior| S3[(Private S3 frontend)]
    CF -->|HTTP; /api and /api/*| ALB[Application Load Balancer]
    ALB --> ECS[ECS backend tasks on EC2]
    ECS --> RDS[(Private RDS PostgreSQL)]
    ECS --> CW[CloudWatch Logs]
    EC2[Private EC2 capacity] -->|ECR, ECS, SSM, Secrets Manager and CloudWatch Logs APIs| VPCE[VPC endpoints]
```

The following describes the template-defined target flow; deployment is pending. The static frontend uses a private S3 bucket served through CloudFront. CloudFront forwards `/api` and `/api/*` to an internet-facing Application Load Balancer. The ALB routes requests to healthy ECS backend tasks running on EC2 capacity in private application subnets. Backend tasks connect to private RDS PostgreSQL; the awslogs driver forwards container output to CloudWatch. Private EC2 instances use only the VPC endpoints needed for AWS service access; no NAT Gateway is planned. The initial public entry point uses the AWS-provided CloudFront hostname over HTTPS. CloudFront connects to the ALB DNS name over HTTP on port 80; this hop is unencrypted.

All cross-stack exports and imports use the same `fit-track-${Environment}-<stack-key>-<output-logical-ID>` naming scheme. `Environment` is currently `prod`; no export name uses `AWS::StackName`. ## ECR scanning template

`infra/ecr.yaml` defines stack `fit-track-prod-ecr` with backend and migration repositories and configures the regional private registry in `eu-central-1` for BASIC image scanning on push. The `fit-track-${Environment}-*` wildcard covers both repositories; repositories outside that prefix remain on manual scanning.

| `EcrMigrationRepository`           | `fit-track-prod-migration-eu-central-1` | Private repo; AES-256 encryption; immutable tags except `main` and `latest`; retain the 10 newest images.             | `Name`, `Environment=prod`, `Project=fit-track`, `Component=ecr`. |

Basic scanning detects operating-system package vulnerabilities. It is the lowest-cost option and avoids Amazon Inspector charges; it does not continuously rescan images or cover application-language packages. Enhanced scanning adds OS and language package findings through Amazon Inspector and can incur Inspector charges. Check the current registry scanning settings in `eu-central-1` before deploying: the CloudFormation resource manages the registry-wide scanning configuration, while the filter limits which repositories get scan-on-push. Repository-level scan-on-push settings are omitted because the registry rule owns scanning behavior. Each repository's lifecycle policy keeps the 10 most recently pushed images, across all tags and expires older ones; ECR may take up to 24 hours to apply expiration. This limits rollback images to the retained set, including release tags attached to those images. `EmptyOnDelete: true` means deleting this stack deletes all images in both repositories. The stack is not deployed or AWS-verified.

## ECS service template

`infra/service.yaml` defines stack `fit-track-prod-service`. It defines two empty runtime secrets, backend and migration execution roles, a backend task definition, and a one-off migration task definition. The secrets are named `fit-track/prod/backend` and `fit-track/prod/migration`; their values are deliberately omitted from CloudFormation and must be added through Secrets Manager after the stack is deployed, before starting tasks. Both JSON secrets use the key `DATABASE_URL` for the same database and endpoint, with separate database users: the backend user has application data permissions, while the migration user has schema migration permissions. Database users and grants are not created by this service template. Store only sensitive production values needed by the backend in the JSON secret; supply ordinary runtime configuration as ECS environment variables. Do not copy local `.env` files or frontend build variables into this secret. Database credential handling depends on the selected RDS authentication method. ### Before deployment

1. **Capacity provider bootstrap.** The template now defaults to `CapacityMode=bootstrap`, creating an ASG with minimum and desired capacity zero before association. See [AWS capacity-provider bootstrap guidance](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/asg-capacity-providers.html).

2. **Task memory compatibility.** Backend and migration task memory now allow only 512 or 1024 MiB, excluding the incompatible 2048 MiB choice on `t3.small`. Larger tasks require a reviewed host-size change. Verify actual registered memory and placement capacity after activation; local validation does not establish workload capacity. Validate `MinSize <= DesiredCapacity <= MaxSize` before compute updates. 3. **Protect deployed image digests.** Both ECR lifecycle rules expire older images across all tags after the count exceeds ten. They do not explicitly protect the deployed revision or rollback revision. An expired deployment digest can prevent a replacement task from pulling its image even while existing tasks continue running. Preview the policy against multi-platform images and retain deployed/rollback digests independently of the build count; untagged-only cleanup is a conservative initial alternative. `EmptyOnDelete: true` also removes repository contents during stack deletion. See [ECR lifecycle evaluation](https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html).

4. **Complete private database bootstrap.** Database users, grants, and runtime secret values remain external prerequisites. The RDS SG permits only the task SG, so a laptop or the EC2 host cannot connect directly under current rules. ### Security and operational refinements

- **Origin trust and HTTP transport.** The ALB prefix list permits all CloudFront distributions and the listener forwards every accepted request. Add an origin custom-header condition with default 403 to restrict forwarding to requests possessing the application's secret. The current origin connection remains HTTP; HTTPS requires an appropriate origin domain and regional ALB certificate. Treat this as a documented transport limitation until addressed. See [AWS ALB origin restriction](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/restrict-access-to-load-balancer.html).

- **EC2 agent isolation and logging.** Explicitly set `ECS_AWSVPC_BLOCK_IMDS=true` to prevent awsvpc application containers from obtaining instance-profile credentials. IMDSv2 is already required, but explicit task isolation avoids depending on metadata hop-limit defaults. Set `ECS_ENABLE_AWSLOGS_EXECUTIONROLE_OVERRIDE=true` to make intended per-task log permissions explicit. Missing the latter is not a confirmed startup blocker: the current instance managed policy already grants log writes. See [task metadata isolation](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html#ecs-task-roles-additional-configuration-for-ec2), [awslogs permissions](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/using_awslogs.html), and [execution-role configuration](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_execution_IAM_role.html).

- **SSM feature scope.** The S3 gateway policy permits only ECR image layers, and the instance role has no selected SSM S3 bucket permissions. Basic Session Manager is not shown to be broken, but SSM Agent updates and documents downloading S3 modules are unsupported through this policy. Add scoped instance-role and endpoint-policy access to the specific AWS-managed buckets for supported operations, or document those operations as unavailable. `ec2messages` may be unnecessary with a sufficiently recent SSM Agent using `ssmmessages`; verify the resolved AMI/agent before removing it. See [SSM private connectivity](https://docs.aws.amazon.com/systems-manager/latest/userguide/setup-create-vpc.html) and [SSM bucket permissions](https://docs.aws.amazon.com/systems-manager/latest/userguide/ssm-agent-technical-details.html#ssm-agent-minimum-s3-permissions).

- **Scheduling and replacement capacity.** A `t3.small` provides two awsvpc task ENI slots after its primary ENI; the default pair of instances provides four slots in aggregate. This is enough in aggregate for two backend tasks, one deployment surge task, and one migration task, but per-AZ memory and ENI availability still govern placement. Larger task settings, concurrent migrations, AZ loss, and instance refresh require capacity analysis. Managed draining and scale-in protection are configured consistently; serialize compute refresh and schema rollout rather than assuming standalone migration tasks restart automatically. See [awsvpc limits](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-networking-awsvpc.html) and [managed instance draining](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/managed-instance-draining.html).

- **CloudFront error caching.** Normal API caching is disabled, but error caching has separate rules. The template now explicitly sets the minimum error TTL to zero for supported cacheable 4xx/5xx responses and preserves their original status and body. The setting applies to both origins; caching-enabled S3 responses retain AWS's one-second minimum. Verify readiness recovery, transient backend errors, and missing assets after deployment; runtime behavior remains unverified. See [CloudFront error caching](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/custom-error-pages-expiration.html).

- **Verification automation and recovery.** `infra:check` is currently local-only. Add a pinned cfn-lint check to GitHub Actions so future template changes receive the same validation. Before describing the platform as production-verified, establish alarms for unhealthy targets, task capacity/failures, RDS free storage/connections, and deployment failures; define restore and rollback procedures. With the current HTTP 80 rule, CloudFront's prefix-list weight is 55; adding separate 443 and 80 rules can exceed the default 60-rule SG quota. See [managed prefix-list weights](https://docs.aws.amazon.com/vpc/latest/userguide/working-with-aws-managed-prefix-lists.html).

Actual ECS registration, secret retrieval, image pulls, log delivery, ALB health routing, secure cookies and CSRF, RDS TLS/failover, and backup restoration remain unverified. They require AWS runtime evidence; the smaller deployable variant can validate shared application behavior, but cannot establish EC2 capacity-provider or Multi-AZ failover behavior for this variant.

## Cost and lifecycle direction

This architecture cannot remain continuously available at zero cost. An ALB, running EC2 capacity, running RDS, and interface VPC endpoints can create ongoing charges. Runtime resources should be created when needed for testing or deployment. During a long pause, billable runtime resources can be stopped or deleted while retaining only data or artifacts worth their storage cost. Record retained, stopped, or removed resources and their verification results here.

Stopping task execution does not remove endpoint, ALB, storage, secret, or retained-data charges. The current compute template keeps at least two EC2 instances in active mode (initial bootstrap launches none), and RDS is Multi-AZ; no free-plan variant is implemented. Confirm current account-plan restrictions and pricing before deployment. RDS deletion protection and retained S3 buckets, database snapshots, and automated backups require explicit teardown decisions.
