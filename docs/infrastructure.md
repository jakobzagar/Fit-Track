# AWS infrastructure

CloudFormation templates are grouped by independently deployed stack and lifecycle. Each stack lives in its own `<stack-key>.yaml` file directly under `infra/`; stack-specific parameters and resources stay together. AWS architecture, decisions, deployment state, and verification are tracked in [the AWS deployment plan](aws-deployment-plan.md).

## Stack boundaries

| Stack       | CloudFormation stack name  | Template                                  | Owns                                                                                                                                  | Depends on                                     |
| ----------- | -------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `network`   | `fit-track-prod-network`   | [network.yaml](../infra/network.yaml)     | VPC, six subnets, internet gateway, route tables, public route                                                                        | None                                           |
| `endpoints` | `fit-track-prod-endpoints` | [endpoints.yaml](../infra/endpoints.yaml) | ECR/ECS/SSM/Secrets Manager/CloudWatch Logs interface endpoints, S3 gateway endpoint, endpoint security group                         | `network`                                      |
| `compute`   | `fit-track-prod-compute`   | [compute.yaml](../infra/compute.yaml)     | ECS cluster, capacity provider, EC2 Auto Scaling group, instance role/profile/security group                                          | `network`, `endpoints`                         |
| `ecr`       | `fit-track-prod-ecr`       | [ecr.yaml](../infra/ecr.yaml)             | Backend and migration repositories; BASIC scan-on-push; retain 10 newest images                                                       | None                                           |
| `logs`      | `fit-track-prod-logs`      | [logs.yaml](../infra/logs.yaml)           | Backend and migration CloudWatch Logs groups with 30-day retention                                                                    | None                                           |
| `ingress`   | `fit-track-prod-ingress`   | [ingress.yaml](../infra/ingress.yaml)     | ALB, HTTP listener, and backend IP target group, and CloudFront-facing security group                                                 | `network`                                      |
| `service`   | `fit-track-prod-service`   | [service.yaml](../infra/service.yaml)     | ECS backend service and task definitions, migration task, IAM roles, runtime secrets, and backend task networking                     | `network`, `compute`, `ingress`, `ecr`, `logs` |
| `database`  | `fit-track-prod-database`  | [database.yaml](../infra/database.yaml)   | Private Multi-AZ PostgreSQL instance with one standby, TLS parameter group, subnet group, and task-restricted database security group | `network`, `service`                           |
| `frontend`  | `fit-track-prod-frontend`  | [frontend.yaml](../infra/frontend.yaml)   | Private frontend bucket, OAC, CloudFront distribution, and API routing; SPA and headers pending                                       | `ingress`                                      |

Deploy `network` → `endpoints` → `compute`. The `database` stack creates the PostgreSQL instance, parameter group, subnet group, and security group, importing the task SG from `service`; deploy it after `network` and `service`, and delete it before either. Bootstrap `service` with zero tasks before deploying `database`. The `ingress` template depends on `network` and uses the verified CloudFront origin-facing prefix-list ID `pl-a3a144ca` for `eu-central-1`. Its HTTP listener forwards to the target group imported by the backend ECS service. The `ecr` and `logs` stacks have no infrastructure dependency; deploy `ecr` before pushing images and `network`, `endpoints`, `compute`, `ingress`, `ecr`, and `logs` before `service`. The ECR scanning resource configures the whole private registry in `eu-central-1`, so check any existing registry scanning configuration before deploying it. The endpoint stack imports network outputs. The compute stack imports network outputs and the endpoint security group ID, then adds an ingress rule that permits HTTPS only from its ECS instance security group. Its Auto Scaling group waits for that rule before launching instances. The service stack imports the network VPC ID and the ingress ALB SG ID. It imports compute capacity, app subnets, and the ingress target group for its ECS service. It owns the backend task ingress rule permitting ALB traffic on port 3001; both groups allow all outbound traffic; ingress does not import service. It also imports backend and migration repository ARNs from `ecr`, their log group ARNs from `logs`, and both repository URIs and log group names. Backend and migration execution roles have separate scoped permissions. Its one-off migration task is run on compute capacity in private app subnets, using the Secrets Manager endpoint. Pass verified backend and migration image digests and populate the stack-created backend and migration secrets before running tasks; the AWS deployment plan owns the migration execution procedure. The backend ECS service is configured with two tasks by default; bootstrap with zero until secrets, database connectivity, and migrations are ready. The AWS plan owns the bootstrap sequence. Deploy each stack with the name `fit-track-${Environment}-<stack-key>` shown above. Imports and exports both use `fit-track-${Environment}-<stack-key>-<output-logical-ID>`, so no stack-name parameters are required. Export names are independent of the deployed CloudFormation stack name; the documented stack naming convention remains the deployment standard. Only one producer of each export may exist in an account and Region. Pass shared resource IDs through CloudFormation exports and `Fn::ImportValue`; imports must be in the same account and Region, and an export cannot be changed or deleted while another stack imports it. Delete `service` before `ecr`, `logs`, and `compute`; delete `service` before `ingress` because the service and its task ingress rule import ingress resources. Delete `compute` before `endpoints`, and delete `ingress` and `endpoints` before `network`.

Add an `infra/<stack-key>.yaml` file when its stack template is ready. The frontend stack imports the ALB DNS name from `ingress`; deploy it after ingress and delete it before ingress. SPA rewriting and frontend response headers remain pending. Pass the frontend URL as the service ClientOrigin parameter.

Run `npm run infra:check` to format-check and lint the CloudFormation templates for `eu-central-1`.

## Resource naming

Regional resource names and Name tags use `fit-track-${Environment}-<resource>-${AWS::Region}`. S3 bucket names additionally include `${AWS::AccountId}` for global uniqueness. Region-scoped secrets and log groups keep their path names, and cross-stack exports retain `fit-track-${Environment}-<stack-key>-<output-logical-ID>`. IAM managed-policy ARNs use `${AWS::Partition}`. The global CloudFront OAC has no regional suffix. The ALB target group's physical name omits the region to stay within its 32-character limit; its Name tag includes the region.

The selected deployment Region remains `eu-central-1`. Network AZ IDs `euc1-az1` and `euc1-az2`, ingress CloudFront prefix-list ID `pl-a3a144ca`, and the bundled RDS CA certificates are region-specific. Dynamic names alone do not make these stacks deployable in another Region; validate or change these settings first.
