# Fargate / Single-AZ infrastructure

This is the deployment architecture intended for actual application hosting on the project's AWS free-plan account. It reduces the infrastructure footprint and operational work through ECS Fargate in one private application subnet, one backend task, and a private Single-AZ RDS PostgreSQL instance. The network, endpoints, compute, service, ingress, ecr, logs, database, and frontend templates are present; AWS deployment remains unverified. Architecture decisions, implementation state, and verification belong in the [AWS deployment plan](../../docs/aws-deployment-plan.md).

The [EC2 / Multi-AZ variant](../ec2-multi-az/README.md) preserves the advanced reference templates for demonstrating AWS infrastructure design, managed EC2 capacity, and Multi-AZ availability. The two directories represent alternative architectures, not staging and production environments. Single-AZ describes application task placement and the database instance; the ALB and RDS subnet group still require subnets in two Availability Zones.

The endpoint stack imports `VpcId`, `AppSubnetAz1Id`, and `AppRouteTableId` from the network stack. The service stack owns TCP 443 ingress from the Fargate task SG to the endpoint SG; backend service creation depends on this rule. SSM and SSM Messages support a temporary private EC2 administration instance for RDS setup through Session Manager port forwarding. That instance requires an SSM instance profile, TCP 443 access to the endpoint SG, and TCP 5432 access to the RDS SG; the administration instance and its additional rules are managed separately from these templates. Use SSM Agent 3.3.40.0 or newer, which prefers `ssmmessages`; the legacy `ec2messages` endpoint is omitted. ECS control-plane endpoints remain omitted and ECS Exec remains disabled. The S3 gateway still permits only ECR layers, so SSM Agent updates and S3-based administration scripts require separate scoped access. See [AWS Fargate endpoint requirements](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

Formatting and cfn-lint pass for all templates. AWS checks confirmed the deployed RDS instance, runtime secret retrieval by ECS, and migration exit code 0. A local backend-user query through the SSM tunnel succeeded. Backend readiness remains pending after a stored URL whitespace issue was identified. The [AWS deployment plan](../../docs/aws-deployment-plan.md#bootstrap-verification) records deployed IDs, evidence, and remaining verification limits; secret values are not stored in the repository.

## Deployment and validation

`network-AvailabilityZoneAz1Name` exports `DbSubnetAz1.AvailabilityZone`, the account-specific AZ name corresponding to `euc1-az1`. The export remains available to other consumers; database does not import it. RDS selects an available AZ from the two-AZ DB subnet group. The database remains Single-AZ and may use a different AZ from Fargate tasks, with possible cross-AZ data transfer charges.

Both task definitions default to 256 CPU units and 512 MiB. CloudFormation rules permit 256 CPU with 512/1024/2048 MiB, 512 CPU with 1024/2048 MiB, and 1024 CPU with 2048 MiB. Fargate placement strategies are omitted and AZ rebalancing is disabled. Backend health-check grace is fixed at 60 seconds to allow startup before ECS acts on unhealthy checks; it does not make an unhealthy ALB target eligible for traffic. Runtime secrets are manually created outside CloudFormation: IAM `Resource` needs the full secret ARN, while task `ValueFrom` must select the relevant JSON key for multi-key secrets. Both execution roles and task definitions reference the full ARN of their respective manually created secret; backend selects `DATABASE_URL` and `JWT_SECRET`, while migration selects only `DATABASE_URL`.

The network, compute, and logs stacks have no cross-stack dependencies. Compute creates only the cluster; service and RunTask requests will configure task networking, CPU/memory, and desired count. Deploy endpoints after network. Service depends on network, endpoints, compute, logs, ingress, and ECR. Database depends on network and the service stack because its ingress rule imports `BackendTaskSecurityGroupId`; it cannot be deployed before that export exists. Create service with zero backend tasks before database provisioning. RDS deletion protection must be disabled before stack deletion; deletion/replacement snapshots and retained automated backups require explicit cleanup decisions. The PostgreSQL minor version, instance class, storage settings, and account-plan eligibility must be checked against AWS before deployment. Database users and grants must be prepared before migrations and backend startup; follow the [PostgreSQL bootstrap procedure](../../docs/aws-deployment-plan.md#postgresql-bootstrap-and-runtime-credentials). Runtime secret values stay outside CloudFormation and the repository.

Run `npm run infra:check` after adding or changing templates. See [infrastructure validation](../../docs/testing.md#infrastructure-validation) for prerequisites and limitations. Account-plan eligibility and resource charges must be checked before deployment; this variant does not imply zero-cost hosting.

The existing EC2 templates use physical names and exports without a variant namespace. Resolve naming and review the shared regional scanning configuration before deploying both variants in the same account and Region.

## Security group conventions

Each `AWS::EC2::SecurityGroup` owns its description, tags, and explicit allow-all IPv4 egress. Inbound permissions are separate `AWS::EC2::SecurityGroupIngress` resources. `ingress` owns CloudFront-to-ALB TCP 80; `service` owns ALB-to-task TCP 3001; `database` owns task-to-RDS TCP 5432. Endpoint HTTPS ingress is owned by `service` for Fargate tasks. Cross-stack rules stay with the consumer stack to keep imports one-way.

## Resource lifecycle

Every resource explicitly declares deletion and replacement policies. S3 buckets, ECR repositories, log groups, and standalone secrets use `Retain`; RDS instances use `Snapshot`; all other resources use `Delete`. The [AWS lifecycle policy table](../../docs/aws-deployment-plan.md#resource-deletion-and-replacement-policies) records the rationale, cleanup requirements, and verification limits. Retained resources require deliberate cleanup or import before recreating stacks with the same names.

## YAML conventions

String values use double quotes, including resource types, policy values, names, descriptions, and scalar arguments to `!Ref`, `!Sub`, and `!GetAtt`. Mapping keys remain unquoted. Numbers and booleans retain their native YAML types; numeric strings required by AWS schemas remain quoted. Multiline JSON, scripts, and function code use block scalars (`|`) without wrapping the content in quotes.
