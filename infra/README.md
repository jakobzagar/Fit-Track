# AWS infrastructure

CloudFormation templates are grouped by independently deployed stack and lifecycle. Each stack lives in `<stack-name>/template.yaml`; stack-specific parameters and resources stay together. AWS architecture, decisions, deployment state, and verification are tracked in [the AWS deployment plan](../docs/aws-deployment-plan.md).

## Stack boundaries

| Stack directory | CloudFormation stack name  | Template                  | Owns                                                                                                                                     | Depends on                              |
| --------------- | -------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `network/`      | `fit-track-prod-network`   | `network/template.yaml`   | VPC, six subnets, internet gateway, route tables, public route                                                                           | None                                    |
| `endpoints/`    | `fit-track-prod-endpoints` | `endpoints/template.yaml` | ECR/ECS/SSM/Secrets Manager/CloudWatch Logs interface endpoints, S3 gateway endpoint, endpoint security group                            | `network/`                              |
| `compute/`      | `fit-track-prod-compute`   | `compute/template.yaml`   | ECS cluster, capacity provider, EC2 Auto Scaling group, instance role/profile/security group                                             | `network/`, `endpoints/`                |
| `ecr/`          | `fit-track-prod-ecr`       | `ecr/template.yaml`       | Backend and migration repositories; BASIC scan-on-push; retain 10 newest images                                                          | None                                    |
| `logs/`         | `fit-track-prod-logs`      | `logs/template.yaml`      | Backend and migration CloudWatch Logs groups with 30-day retention                                                                       | None                                    |
| `ingress/`      | `fit-track-prod-ingress`   | `ingress/template.yaml`   | ALB, HTTP listener, and backend IP target group, and CloudFront-facing security group                                                    | `network/`                              |
| `service/`      | `fit-track-prod-service`   | `service/template.yaml`   | ECS backend and migration task definitions, execution roles, separate backend and migration runtime secrets, and backend task networking | `network/`, `ingress/`, `ecr/`, `logs/` |

Deploy `network` → `endpoints` → `compute`. The `ingress` template depends on `network` and uses the verified CloudFront origin-facing prefix-list ID `pl-a3a144ca` for `eu-central-1`. Its HTTP listener forwards to the target group that the future ECS service will import. The `ecr` and `logs` stacks have no infrastructure dependency; deploy `ecr` before pushing images and `network`, `ingress`, `ecr`, and `logs` before `service`. The ECR scanning resource configures the whole private registry in `eu-central-1`, so check any existing registry scanning configuration before deploying it. The endpoint stack imports network outputs. The compute stack imports network outputs and the endpoint security group ID, then adds an ingress rule that permits HTTPS only from its ECS instance security group. Its Auto Scaling group waits for that rule before launching instances. The service stack imports the network VPC ID and the ingress ALB SG ID. It owns the standalone backend task ingress rule permitting ALB traffic on port 3001; both groups allow all outbound traffic; ingress does not import service. It also imports backend and migration repository ARNs from `ecr`, their log group ARNs from `logs`, and both repository URIs and log group names. Backend and migration execution roles have separate scoped permissions. Its one-off migration task is run on compute capacity in private app subnets, using the Secrets Manager endpoint. Pass verified backend and migration image digests and populate the stack-created backend and migration secrets before running tasks; the AWS deployment plan owns the migration execution procedure. The backend task definition is configured; the ECS service remains pending. Deploy each stack with the name `fit-track-${Environment}-<stack-directory>` shown above. Imports derive their export names from this convention and `Environment`, so no stack-name parameters are required. Exports use `${AWS::StackName}-<output-logical-ID>`; the deployed stack names must match the convention. Pass shared resource IDs through CloudFormation exports and `Fn::ImportValue`; imports must be in the same account and Region, and an export cannot be changed or deleted while another stack imports it. Delete `service` before `ecr`, `logs`, and `compute`; delete `service` before `ingress` because its task ingress rule imports the ALB SG. Delete `ingress` and `endpoints` before `network`.

Create a stack directory when its template is ready; keep the repository free of empty stack placeholders. Future database and frontend stacks are not present yet; add them here when their templates are created.

Run `npm run infra:check` to format-check and lint the CloudFormation templates for `eu-central-1`.
